# 商业项目接入原则

## 1. 选择性接入

宿主项目只选择需要的模块。例如只使用网络接入时，不应被迫引入地图、导航或热更。模块可依赖固定 Skynet 运行时和少量稳定合同，但不通过隐式依赖拉入其他横向模块。

## 2. 显式组装

宿主 composition root 负责：

```text
读取并校验宿主配置
创建所选模块
传递 Service handle 和 Adapter
确定启动、停止和故障策略
把模块结果映射为宿主业务动作
```

框架不读取某台机器的固定路径，不猜测宿主 Service 名，不扫描业务目录寻找实现。

## 3. Adapter 隔离

宿主的 Protobuf 消息、账号对象、战斗实体和配置表停留在 Adapter 外侧。模块使用自己的小型 request/result contract。这样不同商业项目可使用不同协议和数据模型，而无需 fork 框架核心。

## 4. 升级与回滚

商业项目固定模块版本并记录配置/协议/资产版本。升级先在兼容矩阵和测试环境验证，再灰度进入目标环境。涉及持久或长期运行状态时，迁移必须可审计、可中止，并保留回滚条件。

## 5. 发布载体待定

当前不预设 Git submodule、源码 vendor、二进制包或私有包仓库。出现第二个真实消费者后，以以下条件选择：

- 能固定和审计版本；
- 能离线或可重复构建；
- 升级 diff 清晰；
- 不允许宿主静默修改框架源码；
- 支持紧急修复、回滚和多项目兼容窗口。
