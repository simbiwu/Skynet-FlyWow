# 模块准入与完成标准

## 1. 准入条件

课程或商业项目中的能力同时满足以下条件，才进入 Skynet-FlyWow：

1. 解决跨项目基础设施问题，不包含具体游戏业务规则。
2. 至少有一个真实调用者和可运行实现。
3. owner、依赖方向、成功和失败语义已经明确。
4. 核心行为已有测试，迁入后可以脱离原业务独立验证。
5. 不要求复制业务 DTO、配置表或场景代码才能运行。

不满足时继续留在原项目演进。不要用占位接口、空 Service、未来 DTO 或空目录抢先进入框架。

## 2. 最小模块内容

一个可交付模块至少包含当前功能真正需要的：

- Runtime/Tooling 实现；
- 小而明确的公开入口；
- 配置或固定参数说明；
- 成功、边界和失败路径测试；
- README：解决的问题、非目标、依赖、接入和验证；
- 必要的升级或兼容说明。

只有模块真实需要时才增加：

- 独立 Service；
- Native Binding；
- Client SDK；
- 配置 example；
- 运维诊断；
- migration/rollback 工具；
- metrics 或健康检查。

不要为了满足“模块标准”创建没有实际调用者的配套组件。

## 3. API 质量

公共 API 应让宿主明确知道：

- 输入和结果是什么；
- 是否跨 Service；
- 是否 yield 或 I/O；
- 谁拥有返回对象或资源；
- 调用失败时如何判断。

调用方不应通过解析日志文本判断业务结果。

配置、协议和外部输入在边界完成必要校验；内部实现可以依赖已经验证的不变量。

代码排版、注释和语言级规则统一执行：

```text
.agents/skills/skynet-flywow-coding-standard/SKILL.md
```

本文件不重复维护编码规范。

## 4. 资源与失败

只针对模块实际拥有的资源和状态定义 owner、释放和失败行为。

如果资源会持续积累或可能耗尽，再定义容量或过载行为。

不要因为本节存在，就主动给模块增加限流、重试、缓存、队列、监控或其它策略。

重试、限流、缓存等策略必须来自真实需求或明确故障模型，不属于所有商业模块的默认标配。

## 5. 易接入

首次接入者应能通过模块 README 和必要示例完成：

```text
确认固定依赖
提供最小配置或参数
创建/加载模块
执行一个真实调用
观察成功与失败
正常停止并释放资源
```

如果模块没有配置、没有独立 Service 或没有 shutdown 行为，不要为了凑齐流程虚构对应步骤。

## 6. 地图与寻路附加边界

地图或寻路模块需要明确：

- 空间类型、坐标轴、原点、Cell 尺寸和单位；
- `map_id`、`map_version`、资产格式版本和内容 hash；
- 长期公共位置不把内部 Grid 索引当成业务坐标；
- 离线资产输入与 Runtime 加载边界；
- 地图/寻路不依赖 Gateway；
- 未实现的运动模型明确列为非目标。

只有真实支持新的空间或运动模型后，才增加相应公共抽象。

## 7. 文档要求

每个已交付模块使用：

```text
docs/<module>/README.md
```

作为文档入口。

文档覆盖当前模块真实存在的内容：

- 解决的问题和非目标；
- 固定依赖；
- 构建和接入入口；
- 公开 API / Service 消息；
- 实际配置项；
- 生命周期和必要 ownership；
- 主要失败行为；
- 测试/验证入口；
- 已知兼容和未验证范围。

复杂协议、跨端握手、资产格式等确实需要独立说明时再拆分文档，并从 README 链接。

不要为每个知识点单独写教程文档。不要重复解释源码中已经明显的实现细节。

源码或公开合同变化时，只同步受影响的文档，不机械改写全部说明。

## 8. 完成定义

模块完成的标准是当前承诺能力已经：

```text
实现
构建
实际运行或被真实调用验证
通过相关成功/边界/失败测试
具有足够接入说明
```

编译通过不能替代运行验证。

Benchmark 只有在需要形成性能结论时才执行，并记录版本、硬件、负载和测试条件。

没有验证的范围明确写为 `not verified`，不得用“商业级”“完整支持”等词替代证据。
