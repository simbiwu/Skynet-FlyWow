> 用途：实现开始后供查询的执行依据，整理自用户提供的完整方案。
> 优先级：用户最新消息中的“六、Service 私有状态与内部函数更新”为该部分唯一权威版本。本文合并重复的第六节，不改变合同。
> 本文件是临时工作文档，不替代 FLYWOW 的 AGENTS.md、编码 Skill、测试规范或最终模块 README。

## 1. 目标合同

HotUpgrade 只支持在**现存 Skynet Service、现存 Lua State 内原地更新 Lua 代码及必要业务状态**。Service handle、Lua State、模块表身份保持不变。普通模块按完整 Patch 更新；同一事务可选地更新 Service 私有状态与指定业务函数。失败时尽力恢复旧代码和状态；无法确认恢复时报告 `RECOVERY_REQUIRED`、保持 Guard 关闭，不得声称回滚成功。

## 2. 禁止范围

删除或不再实现：候选 Service 启动、Service 替换与退休、Router、灰度切流、候选状态准备、跨 Service 状态搬运，以及仅服务于替换的 `origin_service_handle` 和候选身份字段。

不保留独立 Registry、Runtime、Adapter、RPC 封装、迁移注册表、通用 Patch/状态迁移框架、`apply_modules` 并行入口；不新增 `migrations/`、`service_patches/` 等目录。不为更新单函数增加稳定包装层、函数注册表或间接调用；不为远程认证、管理 UI、多节点发布、Native 热替换预留架构。

不保留并行实现，不改无关模块。不得为减文件而制造巨大函数。删除前确认真实引用和消费者。

## 3. 唯一更新流程

```text
现存 Service 启动并登记
 -> hotupgrade.require 声明当前 Lua State 的可更新模块
 -> Controller 选择已登记目标
 -> Controller 直接向现存目标 Service handle 发送 Skynet 消息
 -> 目标在自己的 Lua State 执行 Stage、Activate 或恢复
```

Controller 不得用自己的 `require` 访问其他 Service 的模块状态；不得 `skynet.newservice` 创建候选；不再包 RPC 封装。`hotupgrade.require` 继续负责本 Lua State 的模块加载和更新登记。不新增第二套更新入口。模块更新、可选 Service 更新、dry-run 和恢复复用同一 Controller、Guard、Stage、Activate、Abort 流程。

## 4. 普通模块完整 Patch

每个 `modules/xxx.lua` 是该模块的完整新版本，即使只改一个函数也提交完整模块文件。

- Stage 加载、编译和检查完整新模块。
- 提交时保留旧模块表身份及 `package.loaded[name]` 对原表的引用。
- 更新新版本全部导出字段，删除旧版有而新版没有的字段；直接替换函数，不加稳定包装。
- 不承诺自动更新其他模块缓存的旧函数引用，文档不得声称支持。
- 新代码生成新闭包；不假设旧 upvalue 自动迁移，禁止用 `debug.upvaluejoin` 等按名/索引盲目搬运。
- 需保留的模块私有状态用模块自己的可选 `export_state` / `import_state` 成对处理；无须保留时不强制钩子，必要钩子缺失则拒绝更新。
- 快照须与旧状态隔离。钩子不得 yield、改其他模块、执行外部 I/O 或产生不可撤销副作用。

## 5. Service 私有状态与内部函数更新（权威合同）

复用现有 Patch 目录的 `services/<service_type>.lua`，改为针对现存 Service 的可选一次性更新脚本，彻底删除其候选 Service 工厂语义。普通模块仍用 `modules/` 完整 Patch。Service 更新脚本可在同一事务中同时修改 Service 私有状态和指定业务函数；必须复用同一个 Controller、Guard、Stage、Activate 和 Abort，不是第二套事务系统。

Service 在自己的 Lua State 提供最小内部更新入口。需要更新的私有状态集中在该 Service 自己作用域的状态表中，不迁移到独立模块，也不要求所有业务状态都改成状态表。

### 5.1 状态所有权

现存 Service 可采用：

```lua
local state = {
    equip = "刀",
    level = 50,
    schema_version = 1,
}

local M = {}

function M.load(item)
    return item.base_attack
end

function M.save(item)
    -- 原有保存逻辑
end
```

`state` 始终由现存 Service 持有，不导出给其他 Service，热更不得替换整个状态表。需热更/迁移的字段放在其中；无关局部变量不要求迁移。

### 5.2 一次性 Service Patch 合同

例如装备由“刀”变为“剑”，等级不变，同时修改 `M.load`：

```lua
return function(state)
    return {
        migrate = function(old_state)
            assert(old_state.schema_version == 1)
            local next_state = {
                equip = old_state.equip,
                level = old_state.level,
                schema_version = 2,
            }
            if next_state.equip == "刀" then
                next_state.equip = "剑"
            end
            return next_state
        end,
        functions = {
            load = function(item)
                local bonus = state.equip == "剑" and 20 or 0
                return item.base_attack + bonus
            end,
        },
    }
end
```

- 构建函数接收现存 Service 私有状态表，返回本次需要的迁移逻辑和业务函数。
- 新函数直接捕获现存 `state`；状态表身份不变，提交后新函数读到新值。
- `migrate` 接收与线上状态隔离的快照，返回完整候选状态，不得直接修改线上状态。
- `functions` 只列要替换的 Service 函数；未列出的（如 `M.save`）保持原样。
- 不加 `M.load` 稳定包装，不建函数注册表。
- 无迁移时省略 `migrate`；无函数更新时省略 `functions`；两者都无时不提供 Service Patch。
- 函数级更新只适用于一次性 Service Patch；`modules/` 下仍用完整 Patch，不支持单字段 Patch。

### 5.3 Service 内部入口与阶段

入口在现存 Service 自己的 Lua State 中：

1. **Stage：**加载更新脚本、执行构建函数、准备新函数，并对独立状态快照运行迁移。
2. 校验候选状态和所有新函数，保存旧状态快照及本次涉及的旧函数字段。
3. **Activate：**先原地更新状态表字段，再直接替换 `M` 中对应函数。
4. 提交失败时恢复旧状态字段和旧函数字段；恢复失败报告 `RECOVERY_REQUIRED` 并保持 Guard 关闭。
5. 更新结束清理快照；成功或确认恢复后才释放 Guard。

迁移和新函数准备不得修改线上状态、产生外部副作用或 yield；提交和恢复也不得 yield。状态表身份不变，候选状态不得替换整个表。更新脚本是受信代码，不是沙箱。快照必须与线上可变状态隔离；无法安全复制的对象由 Service 提供明确快照/恢复处理，不能假称浅拷贝足以回滚。

### 5.4 现有局部变量

若需迁移 `local Equip`、`local Level` 等，优先把需要更新的字段集中到上述私有状态表，仍由原 Service Lua State 持有。不适合入表的状态，由 Service 提供最小内部快照、提交、恢复函数。Controller 不得访问局部变量；不得假设新函数会继承旧 upvalue。禁止通用 Adapter、迁移注册表、候选 Service 或独立 Service Patch 框架。

## 6. 事务、Guard 与失败恢复

### Stage

暂停目标新业务入口并排空在途业务协程；加载、编译、检查全部目标模块；准备必要模块状态导出/导入；准备可选 Service 状态/函数更新；保存恢复所需旧模块导出、旧 Service 状态和旧函数字段。Stage 失败不得改变线上代码或业务状态。

### Activate

在目标 Service 一次同步处理内提交模块和 Service 更新，不得 yield。保持模块表身份；Service 状态仅由 Service 内部入口提交；直接替换指定函数。全部必要校验完成后才能释放 Guard。提交中途失败立即恢复旧模块字段、旧 Service 状态和旧函数字段。

### Abort / Finish

Abort 恢复旧代码和旧状态，确认恢复后才可释放 Guard。Finish 清理快照并恢复业务处理。恢复失败则保持业务入口暂停并报告 `RECOVERY_REQUIRED`。不承诺撤销已发生的数据库写入等外部副作用。

### 多目标、超时、dry-run

多 Service 逐个执行；有的成功、有的失败时报告部分成功，不承诺跨 Service 全局原子回滚。RPC 超时不表示远端操作已取消；结果不确定时不假定目标停止，也不增加 RPC 封装。dry_run 必须验证实际更新和恢复路径，不能只检查文件可加载。本临时方案原包含 validate 管理命令，后续整改已删除；当前发布流程以 README 为准。status 只使用当前进程内事务状态，不维护持久化历史。

## 11. 实施结果与验证（2026-10-19）

本节记录实际交付；前文保留为已确认的实施合同。整改已在 WSL 主工作区的 FlyWow 子模块完成。既有三份其他临时热更稿和根目录未跟踪文件均保留；未修改 Windows 副本，未提交、推送或同步。

### 实际流程与状态合同

- Controller 直接按真实 source handle 登记现存 Service，读取并冻结 Patch 源码，串行协调 prepare → stage → activate → finish；没有替换或并行更新路径。
- hotupgrade.require 继续负责本 State 声明，登记后的首次声明通过原生 Skynet 消息通知 Controller。
- 完整模块 Patch 保留原表与 package.loaded 引用，增加/替换/删除全部导出字段；状态钩子使用独立快照，旧函数缓存不自动更新。
- services/<service_type>.lua 已改为现存 Service 的一次性更新脚本；可单独更新状态、单独替换函数或与模块一起提交。
- 默认状态快照隔离普通数据图并保留图内共享/循环；状态根表身份不变。特殊对象通过 Service 自己的 snapshot/commit/restore 成组处理。
- Stage 失败不安装线上代码；Activate 失败恢复模块、Service 状态与指定函数字段。确认恢复后开放 Guard，恢复不确定则保持暂停并报告 HU_RECOVERY_REQUIRED。
- 多目标按 handle 逐个处理，失败时保留已完成目标并报告 PARTIAL；status 仅保留活动事务及最近终态，没有持久化历史。

### 明确限制

- 脚本与回调是受信同步合同，必须无外部副作用且不得 yield；不提供安全沙箱，不承诺撤销违反合同的行为、阻塞 Native、死循环或 OOM。
- 默认快照只处理普通数据，最多 64 层、10000 个字段；特殊对象隔离和迁移验证由 Service 显式回调负责。仅保证状态根表身份，不保证默认复制后的嵌套表身份。
- 普通模块导出限制为函数和标量；私有状态钩子成对；旧函数缓存不自动更新。

- Controller 重启不恢复登记或事务；恢复门禁要求宿主核对实际状态并人工恢复或受控重启。
- 未验证宿主真实业务、数据库、部署权限、压力或长时间运行。
