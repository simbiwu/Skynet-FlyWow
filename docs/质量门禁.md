# 质量门禁

## 1. 基线原则

每次修改都要给出与风险匹配的证据。文档和仓库配置至少通过仓库自检；具体模块还必须执行自己的 build、运行、成功/边界/失败测试。仓库自检只覆盖基线，不能替代模块验证。

## 2. 当前可执行门禁

在仓库根目录运行：

```bash
python3 -m unittest discover -s scripts/quality -p 'test_*.py'
python3 scripts/quality/check_repository.py
```

第一条验证仓库自检工具本身的成功与失败判断；第二条检查：

- 必要工程文档和 P0 Skill 是否存在；
- 受控文本是否为 UTF-8、LF 且有末尾换行；
- Markdown 是否包含中文正文、代码围栏是否闭合；
- Skill 名称、中文触发描述和初始化占位符是否符合合同；
- 当前 Git 工作区及暂存区中，变更行涉及的非平凡具名 Lua 函数是否有紧邻的职责说明。

Lua 注释门禁通过 `git diff` 对比当前变更与 `HEAD`，并将新增的未跟踪 Lua 文件纳入检查。建议在提交前运行。没有 Git 元数据的源码快照会跳过这项变更检查；它不回溯已提交的历史代码。

## 3. 注释门禁的能力边界

自动检查只负责拦截一类明确遗漏：变更涉及非平凡具名 Lua 函数，但函数声明前没有职责说明。它使用结构启发式区分简单函数，并不理解完整 Lua 语义。

自动检查**不能**证明注释内容正确、充分或符合业务事实，也不能可靠判断所有匿名回调、C/C++ 函数和复杂数据流的可读性。代码交付仍必须依照 `.agents/skills/skynet-flywow-coding-standard/SKILL.md` 对本次新增和实质修改的非平凡函数逐个进行语义审查，尤其检查重要变量、record、不同用途的集合、逻辑阶段、状态变化及失败/生命周期约束。

不得把“脚本通过”当成“注释质量已经通过”，也不得为了让门禁变绿而添加空泛注释。

## 4. 检查范围

仓库自检由开发者按需在本地运行，不会自动执行或代替发布前验证。具体模块还必须在同一变更中增加对应编译、测试、资源清理和必要的集成验证，不能让通用检查器假装覆盖业务行为。

## 5. 结果报告

提交或发布说明分别列出：

```text
build：实际构建的 target
run：实际启动和执行的场景
test：运行的成功、边界和失败用例
quality gate：实际运行的仓库自检与注释门禁结果
not verified：本次没有验证的边界
```

任何失败都先修复首个根因，不通过关闭校验、减少断言或吞掉错误让门禁变绿。
