# 质量门禁

## 1. 基线原则

每次修改都要给出与风险匹配的证据。文档和仓库配置至少通过仓库自检；具体模块还必须执行自己的 build、运行、成功/边界/失败测试。仓库自检只覆盖基线，不能替代模块验证。

## 2. 当前可执行门禁

在仓库根目录运行：

```bash
python3 -m unittest discover -s scripts/quality -p 'test_*.py'
python3 scripts/quality/check_repository.py
```

第一条验证仓库自检工具本身的成功与失败判断；第二条检查：

- 必要工程文档和 P0 Skill 是否存在；
- 受控文本是否为 UTF-8、LF 且有末尾换行；
- Markdown 是否包含中文正文、代码围栏是否闭合；
- Skill 名称、中文触发描述和初始化占位符是否符合合同；
- 当前 Git 工作区及暂存区中，变更行涉及的具名 Lua 函数是否有结构化返回合同、每个业务参数是否有中文用途说明、非平凡函数是否有紧邻职责说明；
- 全仓所有模块中，本次变更的 Lua 函数、record 字段和通用注释表达是否通过通用门禁；
- HotUpgrade 专项门禁是否通过其全量生产/样例扫描及专用术语检查；两层检查在同一个仓库入口中都会执行；
- 变更函数中是否存在与控制头挤在同一行的 if/loop 主体；同级控制块结束后继续执行其他阶段时，边界是否有空行及紧邻该阶段的中文目的说明，不使用函数长度阈值。

本地运行时，Lua 注释门禁通过 `git diff` 对比当前变更与 `HEAD`，并将新增的未跟踪 Lua 文件纳入检查。GitHub Actions 在 Pull Request 和推送到 `main` 时自动执行相同单测，并按 PR 基线或 push 前一提交扫描已提交差异；完整 Git 历史是该差异扫描的必要条件。没有 Git 元数据的源码快照会跳过变更函数检查；该检查不回溯未变更历史代码。

## 3. 注释门禁的能力边界

全仓通用 Lua 门禁对所有 FlyWow 模块的变更 Lua 文件执行：检查变更函数的固定返回合同、业务参数说明、非平凡函数职责注释、阶段分段和压缩控制体；同时检查本次变更的多行 record 字段是否逐项就近说明，并拦截通用含糊注释词表。词表包括“参数/状态检查”“数据准备”“状态修改”“持久化/消息发送”“核心计算”“收尾”等只标阶段名称、没有解释具体操作的写法。它按 Git 差异定位变更，不回溯未改函数和字段。函数范围和复杂度仍通过轻量结构解析识别。

HotUpgrade 专项门禁在全仓通用门禁之外额外执行：hotupgrade/lualib 和 hotupgrade/service 生产 Lua 每次都全量扫描函数合同、分阶段排版、压缩控制体和 Controller 的 load_patch LuaDoc 成员签名；同时扫描 hotupgrade 下 README/课程中的 Lua 围栏代码，拦截已知抽象注释；多行 record 字段门禁只检查生产 Lua 和 hotupgrade/sample、hotupgrade/newsample 中的可运行样例源文件，要求每个具名字段独立书写并带就近说明。教学文档中的片段可能只展示局部代码，不按完整 record 检查字段。其余模块仍执行上述全仓通用门禁；以后增加模块专项门禁时，也必须通过同一个仓库检查入口与通用门禁一起运行。本地门禁仍须按 AGENTS.md 的交付要求执行；CI 是额外自动拦截，不替代本地验证和逐函数人工审查。自动检查能发现多行具名 table/record 中漏掉字段注释或同一行堆叠多个字段，并拦截一组已知抽象套话；它仍不能证明其他注释语义正确、变量/record 首次出现说明充分、每条返回路径都符合返回注释、所有调用者均按合同处理，也不能可靠覆盖匿名回调、C/C++ 函数和复杂数据流。无 Git 元数据时变更函数扫描会跳过；未变更的历史函数不回溯检查。提交前仍须依照编码 Skill 逐项审查本次新增和实质修改的非平凡函数，核对重要变量、record、不同用途集合、阶段、返回分支与调用链、状态变化及失败/生命周期约束；新增或保留状态字段时，确认其真实生产消费者和所驱动决策，不能以既有测试、样例或文档引用作为必要性证明。保留防御状态或重复阶段检查前，沿生产入口证明其要防御的事件在当前调用次数、顺序、批次门禁和重试/重放合同下确实可达；已有调用链保证至多一次或固定顺序时，不为理论上的重复调用增加状态。若测试只覆盖不可达事件，应随防御逻辑删除，但保留真实 yield、失败恢复和正常顺序验证。删除状态时同步清理全部相关引用。

AI 变更还受编码 Skill 中“AI 实施前后合同门禁”约束：改动前核实并列出受影响合同，未获用户明确要求不得更改；改动后对照差异复核签名、返回/错误合同、协议字段、状态生命周期、调用顺序和失败行为。静态脚本可以验证这条规则仍在 Skill 中，但无法证明 AI 实际遵守或自动判断业务合同是否被擅改，仍须在逐函数审查和差异复核中确认。不得把“脚本通过”当成“注释语义或合同审查已经通过”，也不得为了让门禁变绿而添加空泛注释。

## 4. 提交前逐函数人工审查

按 Git diff 列出本次新增和实质修改的函数，逐个确认：

- 函数头、参数和返回注释与实现及全部调用方一致；所有正常返回路径使用同一固定合同，错误边界与原生异常适配行为写明。
- 业务变量、首次使用的 record/table 字段及不同用途的集合均说明来源、当前含义和后续用途；不能仅因名字直观而省略。对本次触及的每个多行 table/record 构造逐字段检查，确认字段说明紧贴构造字段，不能只依赖 LuaDoc 类型定义或表前总注释。
- 多阶段流程按真实边界分段；非显然阶段说明约束/状态变化，注释不复述下一行代码。
- 捕获异常的位置确实是原生接口、候选代码或业务回调边界；内部合同在捕获后已转换，未泄漏 pcall 的布尔值和附加返回值。
- 返回合同变化已沿完整调用链更新，并同步测试、样例和文档。
- 注释不能只包含中文或内部术语；先不看相邻代码读一遍，能否直接说清谁在什么情况下做什么、为什么以及失败后怎么处理。若需要靠追完整调用链、猜“上下文/执行状态/许可/收敛”等词的含义才能读懂，判定未通过；包装 RPC、回调或候选代码时，须说明被调用的实际操作、捕获的失败及转换后的结果。

结构扫描不能替代以上任何语义判断。发现遗漏应在同一变更中修复并重新运行门禁。

## 5. 检查范围

仓库自检由开发者按需在本地运行，不会自动执行或代替发布前验证。具体模块还必须在同一变更中增加对应编译、测试、资源清理和必要的集成验证，不能让通用检查器假装覆盖业务行为。

## 6. 结果报告

提交或发布说明分别列出：

```text
build：实际构建的 target
run：实际启动和执行的场景
test：运行的成功、边界和失败用例
quality gate：实际运行的仓库自检与注释门禁结果
not verified：本次没有验证的边界
```

任何失败都先修复首个根因，不通过关闭校验、减少断言或吞掉错误让门禁变绿。
