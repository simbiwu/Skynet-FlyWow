# 质量门禁

## 1. 基线原则

每次修改都要给出与风险匹配的证据。文档和仓库配置至少通过仓库自检；具体模块还必须执行自己的 build、运行、成功/边界/失败测试。仓库自检只覆盖基线，不能替代模块验证。

## 2. 当前可执行门禁

在仓库根目录运行：

```bash
python3 -m unittest discover -s scripts/quality -p 'test_*.py'
python3 scripts/quality/check_repository.py
```

第一条验证仓库自检工具本身的成功与失败判断；第二条检查：

- 必要工程文档和 P0 Skill 是否存在；
- 受控文本是否为 UTF-8、LF 且有末尾换行；
- Markdown 是否包含中文正文、代码围栏是否闭合；
- Skill 名称、中文触发描述和初始化占位符是否符合合同；
- 当前 Git 工作区及暂存区中，变更行涉及的具名 Lua 函数是否有结构化返回合同、每个业务参数是否有中文用途说明、非平凡函数是否有紧邻职责说明；
- 变更函数中是否存在与控制头挤在同一行的 if/loop 主体；同级控制块结束后继续执行其他阶段时，边界是否有空行及紧邻该阶段的中文目的说明，不使用函数长度阈值。

本地运行时，Lua 注释门禁通过 `git diff` 对比当前变更与 `HEAD`，并将新增的未跟踪 Lua 文件纳入检查。GitHub Actions 在 Pull Request 和推送到 `main` 时自动执行相同单测，并按 PR 基线或 push 前一提交扫描已提交差异；完整 Git 历史是该差异扫描的必要条件。没有 Git 元数据的源码快照会跳过变更函数检查；该检查不回溯未变更历史代码。

## 3. 注释门禁的能力边界

自动检查覆盖当前变更行涉及的具名 Lua 函数：返回注释存在且有中文说明、业务参数注释存在且有中文说明、非平凡函数有紧邻职责说明、单行压缩控制体被拒绝；通过 Lua 代码块结构识别同级控制块结束后的后续处理阶段，并逐个要求阶段边界有空行和紧邻下一阶段的中文目的说明，不按函数行数跳过。函数范围和复杂度仍通过轻量结构解析识别。

HotUpgrade 的 hotupgrade/lualib 和 hotupgrade/service 生产 Lua 每次都全量扫描函数合同、分阶段排版、压缩控制体和 Controller 的 load_patch LuaDoc 成员签名；其余 Lua 文件仍按 Git 变更范围扫描。本地门禁仍须按 AGENTS.md 的交付要求执行；CI 是额外自动拦截，不替代本地验证和逐函数人工审查。自动检查不能证明注释语义正确、变量/record 首次出现说明充分、每条返回路径都符合返回注释、所有调用者均按合同处理，也不能可靠覆盖匿名回调、C/C++ 函数和复杂数据流。无 Git 元数据时变更函数扫描会跳过；未变更的历史函数不回溯检查。提交前仍须依照编码 Skill 逐项审查本次新增和实质修改的非平凡函数，核对重要变量、record、不同用途集合、阶段、返回分支与调用链、状态变化及失败/生命周期约束。

不得把“脚本通过”当成“注释质量已经通过”，也不得为了让门禁变绿而添加空泛注释。

## 4. 提交前逐函数人工审查

按 Git diff 列出本次新增和实质修改的函数，逐个确认：

- 函数头、参数和返回注释与实现及全部调用方一致；所有正常返回路径使用同一固定合同，错误边界与原生异常适配行为写明。
- 业务变量、首次使用的 record/table 字段及不同用途的集合均说明来源、当前含义和后续用途；不能仅因名字直观而省略。
- 多阶段流程按真实边界分段；非显然阶段说明约束/状态变化，注释不复述下一行代码。
- 捕获异常的位置确实是原生接口、候选代码或业务回调边界；内部合同在捕获后已转换，未泄漏 pcall 的布尔值和附加返回值。
- 返回合同变化已沿完整调用链更新，并同步测试、样例和文档。

结构扫描不能替代以上任何语义判断。发现遗漏应在同一变更中修复并重新运行门禁。

## 5. 检查范围

仓库自检由开发者按需在本地运行，不会自动执行或代替发布前验证。具体模块还必须在同一变更中增加对应编译、测试、资源清理和必要的集成验证，不能让通用检查器假装覆盖业务行为。

## 6. 结果报告

提交或发布说明分别列出：

```text
build：实际构建的 target
run：实际启动和执行的场景
test：运行的成功、边界和失败用例
quality gate：实际运行的仓库自检与注释门禁结果
not verified：本次没有验证的边界
```

任何失败都先修复首个根因，不通过关闭校验、减少断言或吞掉错误让门禁变绿。
