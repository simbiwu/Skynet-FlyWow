# 质量门禁

## 1. 基线原则

每次修改都要给出与风险匹配的证据。文档和仓库配置至少通过仓库自检；具体模块还必须执行自己的 build、运行、成功/边界/失败测试。仓库自检只覆盖基线，不能替代模块验证。

自动门禁负责可确定的结构性检查，不判断架构是否合理，也不以行数、类数量、文件大小或抽象层数量机械判定复杂度。设计必要性、重复防御和架构重置仍须按 Engineering Workflow 人工审计。

## 2. 当前可执行门禁

在仓库根目录运行：

```bash
python3 -m unittest discover -s scripts/quality -p 'test_*.py'
python3 scripts/quality/check_repository.py
python3 scripts/quality/check_skill_structure.py
```

现有 `check_repository.py` 检查：

- 必要工程文档和 P0 Coding Standard 是否存在；
- 受控文本是否为 UTF-8、LF 且有末尾换行；
- Markdown 是否包含中文正文、代码围栏是否闭合；
- Coding Standard Skill 名称、中文触发描述和合同门禁是否符合现有检查；
- 当前 Git 工作区及暂存区中，变更行涉及的具名 Lua 函数是否有结构化返回合同、业务参数说明和职责说明；
- 全仓通用门禁、HotUpgrade 专项门禁及 Lua 阶段排版检查。

新增 `check_skill_structure.py` 检查：

- 三个 Skill 入口的路径、Frontmatter、name 和中文 description；
- Coding Standard 与 Engineering Workflow 必需 references 是否存在；
- Skill 中引用的相对 reference 路径是否有效；
- 规范升级验收案例是否存在于复杂度审计文档；
- UTF-8、LF 和末尾换行。

`test_skill_structure.py` 验证检查器对缺失文件、错误 Skill 身份、失效 reference 和正常仓库结构的判断。它与原有测试一起由 unittest discover 执行。

本地运行时，Lua 注释门禁通过 `git diff` 对比当前变更与 `HEAD`，并将新增的未跟踪 Lua 文件纳入检查。GitHub Actions 在 Pull Request 和推送到 `main` 时自动执行相同单测、仓库门禁和 Skill 结构门禁。没有 Git 元数据的源码快照会跳过变更函数检查；该检查不回溯未变更历史代码。

## 3. 注释门禁的能力边界

全仓通用 Lua 门禁对所有 FlyWow 模块的变更 Lua 文件执行：检查变更函数的固定返回合同、业务参数说明、非平凡函数职责注释、阶段分段和压缩控制体；同时检查本次变更的多行 record 字段是否逐项就近说明，并拦截通用含糊注释词表。它按 Git 差异定位变更，不回溯未改函数和字段。

HotUpgrade 专项门禁在全仓通用门禁之外额外执行生产 Lua、样例和教程片段的专用检查。其他模块执行全仓通用门禁；新增模块专项门禁时，必须通过同一个仓库入口与通用门禁一起运行。

结构扫描不能替代语义审查。它不能证明注释真实清楚、所有调用者正确处理返回值、设计复杂度合理或合同未被擅改。提交前仍须按 Coding Standard 和 Engineering Workflow 逐项检查本次变更。

## 4. 最小设计与复杂度审计

用户要求完整模块审计、最小化审计或复杂度整改时，必须使用 `flywow-engineering-workflow` 的代码审计与复杂度审计、反模式与架构重置 references。

重点审查：

- 有调用者但可以由更直接调用替代的中间层；
- 有测试但只绑定内部实现的抽象；
- 内部文档引用但不属于公开合同的结构；
- 同一状态、数据和错误在调用链中重复传递、包装、改名或检查；
- 为多余对象、Context 或调用关系产生的生命周期与保护机制；
- 当前生产路径不可达、只由测试人为构造的防御状态；
- 没有真实消费者的扩展点和通用抽象。

审计必须从真实需求和公开合同独立推导更简单的完整实现，再与当前实现比较。不得因为调用者、测试、文档或现有保护机制存在，就自动判定设计必要；也不得为了代码少而删除真实的安全边界、授权检查、并发保护、资源生命周期或公开合同。

每个问题必须提供代码位置、现状、复杂度来源、真实约束、建议处理、具体替代实现、影响范围和验收标准。证据不足时标记“尚未证实”，不得强行判定保留或删除。

## 5. 提交前逐函数人工审查

按 Git diff 列出本次新增和实质修改的函数，逐个确认：

- 函数头、参数和返回注释与实现及全部调用方一致；
- 业务变量、首次使用的 record/table 字段及不同用途集合说明来源、当前含义和后续用途；
- 多阶段流程按真实边界分段，注释解释约束和状态变化；
- 捕获异常的位置确实是原生接口、候选代码或业务回调边界；
- 返回合同变化已沿完整调用链更新，并同步测试、样例和文档；
- 重要注释能让维护者理解谁在什么情况下做什么、为什么以及失败后如何处理。

结构扫描不能替代以上语义判断。发现遗漏应在同一变更中修复并重新运行门禁。

## 6. 结果报告

提交或发布说明分别列出：

```text
build：实际构建的 target
run：实际启动和执行的场景
test：运行的成功、边界和失败用例
quality gate：实际运行的仓库自检、Skill 结构检查和注释门禁结果
not verified：本次没有验证的边界
```

任何失败都先修复首个根因，不通过关闭校验、减少断言或吞掉错误让门禁变绿。
