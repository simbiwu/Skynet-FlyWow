# 工程架构

## 1. 目标

Skynet-FlyWow 提供可以按需选择的 Server 基础模块。宿主游戏工程拥有 composition root，负责选择模块、注入配置和 Service handle，并连接业务 Adapter。

```text
Commercial Game Application
  -> application composition root
      -> selected Skynet-FlyWow modules
          -> small stable contracts
              -> pinned Skynet / Lua / native runtime
```

依赖只向下。框架不知道宿主项目的战斗、角色、联盟、策划表或业务协议 DTO。

## 2. 边界

- Contract：跨模块或面向宿主的稳定值、错误和版本合同。
- Module：解决一个基础设施问题并拥有自己的状态与生命周期。
- Adapter：连接外部协议、存储、引擎或宿主业务，不让外部类型进入核心合同。
- Composition Root：由宿主拥有，负责选择和连接具体实现。
- Tooling：离线构建、验证、诊断和迁移，不伪装成 Runtime Service。

这些是职责分类，不要求建立对应空目录或基类。

## 3. 公共层

公共层只接受已经被多个真实模块共同使用、语义稳定且没有业务含义的内容。

便利函数、业务 DTO 和“以后可能会用”的抽象留在当前 owner 内。

第二个真实消费者或第二种真实实现出现后，再判断是否提取公共接口。

## 4. 生命周期与 ownership

每个模块只需要把真实存在的关键边界说明清楚：

```text
谁创建、启动、停止和销毁
状态属于哪个 Service / Lua State / native object
哪些调用会 yield、I/O、加锁或跨线程
实际持有的 fd/buffer/queue/timer/cache 等资源由谁释放
真实存在的可增长资源是否需要容量上限
关闭和失败时如何收敛
```

不要因为本节列出了 queue、timer、cache 等名词，就主动给模块创建这些机制。

模块不能通过隐藏的全局名字掩盖必要依赖。需要跨 Service 调用时，由 composition root 或明确父 Service 传入 handle。

## 5. 扩展策略

第一种实现先解决当前问题。

扩展点来自真实的第二种实现或第二个消费者，不来自预测未来。

只有当前确实需要独立消息队列、Lua State、故障隔离或并行 owner 时才增加 Service。

只有当前确实存在不同实现需要选择时才增加 factory/provider/plugin 等机制。

额外能力可能有价值但当前没有需求时，记录建议即可，不进入 Runtime。

## 6. 模块独立性

横向模块不建立无必要依赖：

```text
Gateway     不依赖 Navigation
Navigation  不依赖 Gateway
Logger      不要求宿主接入其它 FlyWow 模块
Battle 核心 不依赖客户端协议
```

商业项目只选择需要的模块，不承担未使用模块的运行时依赖和构建依赖。

## 7. 地图、寻路与战斗

地图公共接入面使用整数世界/逻辑坐标、`map_id`、`map_version` 和内容 hash。

地图 manifest 声明实际需要的空间类型、坐标轴、原点、Cell 尺寸与资产格式版本。

当前实现只承诺已经真实实现并测试的空间和运动模型。未来出现新的真实消费者后再提取共同接口，不提前设计万能地图抽象。

地图资产导入器属于离线 Tooling。Runtime 只加载已经发布和验证的资产，不读取 Unity/H5 工程目录。

## 8. 热更边界

热更作为独立模块演进。

框架负责其明确承诺的顺序、兼容检查、失败结果和必要回滚边界；业务状态的兼容与迁移由业务模块提供。

不要为了“以后可能热更”提前给所有模块增加迁移框架、状态机或版本适配层。

## 9. 交付与兼容

商业项目默认通过 Git submodule 固定 FlyWow 提交。

模块需要能够固定版本、可重复构建和测试，不依赖开发机绝对路径。

公开合同发生破坏性变化时才要求对应迁移说明；内部实现调整不自动升级为公共兼容工程。
