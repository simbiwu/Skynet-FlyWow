# 源码实战教学规范

## 一、核心教学理念

**从零动手，以真实业务问题驱动学习；先建立可观察的运行现象，再沿真实源码深入分析；始终保持完整、连续的执行主线，最终形成独立理解、实现、调试和维护模块的能力。**

课程不能只是源码注释、API 说明、知识点罗列或架构介绍。

学习者需要真正经历：

**真实业务需求 → 遇到具体问题 → 理解问题背景 → 亲手实现最小可运行案例 → 运行观察 → 追踪真实源码 → 深入理解底层机制 → 验证结论 → 扩展与故障实验 → 独立掌握模块。**

重要机制必须深入浅出，使用真实例子、具体数据和可观察的运行结果解释；非重点内容可以简讲，但不能省略理解完整流程所必需的知识。

教学以学习者真正理解为目标，不以快速完成教程或缩短篇幅为目标。

## 二、从零开始，以真实业务案例驱动

### 2.1 必须从具体的工程场景开始

课程开篇应先建立一个真实、容易理解的工程问题，而不是直接介绍类、函数、接口和抽象设计。

例如：

- 学习 Skynet：从 MMO 玩家登录、PlayerService 创建、玩家请求与消息处理开始。
- 学习 AOI：从玩家进入场景、移动、进入或离开其他玩家视野开始。
- 学习网络通信：从客户端发送请求、网关接收、消息分发和业务响应开始。
- 学习数据库模块：从玩家加载角色数据、修改状态、异步保存开始。
- 学习 HotUpgrade：从运行中的 PlayerService 需要更新逻辑且不能丢失玩家状态开始。

上述例子只是教学方法示范，不应限制课程适用范围。

课程应回答：

1. 当前业务要完成什么？
2. 为什么需要这个模块？
3. 没有它时会遇到什么问题？
4. 我们打算通过什么最小案例观察和解决问题？
5. 学完后能够独立完成什么？

**先有业务场景和实际问题，再进入框架机制与源码。禁止抽象概念先行、脱离实际业务空讲设计。**

### 2.2 从零搭建独立 Sample

原则上使用一个独立、最小、真实可运行的教学 Sample 贯穿课程。

这里的“从零”，指学习者从空的教学工程开始，亲手完成 Sample，而不是要求重新实现已经存在的底层框架或目标模块。

Sample 必须：

- 使用真实项目提供的接口和实现。
- 规模适中，贴近实际业务。
- 由学习者跟随课程逐步创建，而非直接交付完成品。
- 不依赖旧课程、旧 Sample 或未说明的人工准备。
- 能够在后续章节持续扩展，形成完整的功能演进过程。

优先复用同一套业务对象、数据和工程结构，通过不同阶段展示新机制。

例如同一个 PlayerService 可以经历初始化、处理玩家请求、功能更新、错误恢复和后续修复，而不必每讲一个概念就创建一个新项目。

### 2.3 学习者必须亲手实施

教程负责指导，不代替学习者完成实践。

每个新建文件应提供：

- 完整文件路径。
- 文件在工程中的作用。
- 为什么需要创建它。
- 可直接照着编写的完整代码。
- 重要代码的解释。
- 编写完成后如何运行或验证。

修改已有文件时必须说明：

- 修改哪个文件、类或函数。
- 原有代码位于哪里。
- 插入、替换或删除哪一部分。
- 修改后的相关代码结构。
- 这一修改如何衔接前面已经实现的功能。

禁止使用“自行补全”“在合适位置添加”“参考前一课的工程”等无法独立执行的说明。

未经明确要求，不得提前替学习者生成整个 Sample 或擅自修改其项目源码。

## 三、以真实运行现象引导源码学习

优先采用：

**先提出问题 → 动手实验 → 观察现象 → 追踪源码 → 解释原因 → 再次验证。**

不能一开始就把大量底层源码摆出来，让学习者在尚未理解问题时被迫阅读实现细节。

例如，学习协程与 Queue：

先构造两个并发玩家请求，让其中一个请求在执行过程中 yield。

观察第二个请求是否进入、何时执行、是否发生并发修改。

再进入实际的 Queue 和协程调度源码，解释为什么出现这个结果。

学习完成后，应能根据源码推导相同或类似场景的执行结果。

但“先观察现象”不能变成只展示结果、不介绍必要背景。开始实验前，必须解释运行所需的最小前置概念和业务条件。

如果某个机制必须先了解底层才能安全或正确实验，可以先解释必要基础，再实施实验。

## 四、必须保持一条完整、连续的教学主线

### 4.1 按真实执行顺序组织内容

课程应遵循业务功能从建立到运行、验证、扩展的自然顺序。

源码讲解也应尽量沿真实调用链推进。

禁止把多个相互关联的函数拆成不连续的知识点，导致学习者虽然知道每个函数的作用，却不知道它们如何协作。

例如学习一次跨 Service 调用，应从发起方开始，依次讲：

1. 为什么发起调用。
2. 调用方执行到哪里。
3. 请求通过什么接口发送。
4. 参数从哪里产生。
5. 消息由谁接收和分发。
6. 接收方调用什么函数。
7. 接收方实际完成什么操作。
8. 是否产生 yield、等待或异步调度。
9. 返回什么结果。
10. 调用方恢复后继续执行什么。

**不能突然跳到被调用函数内部，也不能只给出被调用函数的源码而不说明它如何被执行。**

### 4.2 跨文件、跨执行上下文必须交代清楚

每当调用链跨越以下边界，必须明确说明：

- 不同文件、类、模块。
- 不同线程或协程。
- 不同 Service、Actor、进程或节点。
- RPC、消息队列、异步任务或事件回调。
- 不同语言层，例如 C++ 与 Lua。
- 不同状态或生命周期阶段。

根据实际技术栈选择相关信息，不强行套用不适用的概念。

对于 Skynet 等系统，尤其应标明：

- 当前执行在哪个 Service。
- 属于哪个 Lua State。
- 当前是哪条协程。
- RPC 调用是否 yield。
- 谁等待、谁唤醒。
- 哪些数据属于当前 Service 私有状态。
- 操作是否跨越 Service 边界。

这些执行关系必须与真实源码一致，不能根据一般经验推测。

### 4.3 深入子函数后必须回到主线

当执行到重要函数时，可以暂时进入该函数内部进行深度源码分析。

分析完成后，必须明确说明：

- 当前函数执行完成后返回哪里。
- 返回了什么。
- 调用者恢复到哪一行或哪一逻辑阶段。
- 接下来继续执行什么。

把整个教程当成一条真实调用栈来组织。

任何必要的专题扩展都应有清晰的进入点和返回点。

## 五、每段源码必须具备完整上下文

任何重要代码片段出现前，必须交代：

1. **位置**：真实文件路径、所属类或模块、函数名。
2. **执行现场**：目前处于哪个业务或系统阶段。
3. **调用者**：谁调用这个函数，通过什么路径调用。
4. **调用原因**：为什么此时必须执行它。
5. **输入**：参数、对象和关键变量从哪里来。
6. **前置条件**：执行前哪些状态已经建立。

代码讲解时，需要解释关键分支、重要变量、设计动机，以及它如何处理当前问题。

讲解结束后必须说明：

1. 返回结果。
2. 状态或对象发生的变化。
3. 是否存在尚未完成的等待或异步操作。
4. 下一步由哪个函数或执行上下文继续。

### 大型函数的分段规则

大型函数可以按逻辑拆分，但必须：

- 先说明函数整体职责和主要执行阶段。
- 按实际控制流顺序讲解。
- 每段明确属于该函数的哪个逻辑区域。
- 说明当前片段承接前一段的什么状态。
- 保留理解该段所必需的条件、分支和变量。
- 解释如何进入下一段。

如果为突出核心逻辑而省略部分源码，必须说明省略了什么、为什么不会影响当前讲解；不能把删减后的代码称为完整真实源码。

**禁止突然出现几行孤立代码，然后直接讲它的功能。**

## 六、关键机制必须深入浅出

课程重点由目标模块决定，不机械要求所有内容同样详细。

对核心算法、数据结构、内存关系、并发协调、状态机和生命周期等重要机制，必须做到：

### 6.1 先说明设计动机

不只解释代码做了什么，还要解释：

- 为什么需要它。
- 它解决了哪个具体问题。
- 不这样做会怎样。
- 为什么当前实现选择这种方式。
- 主要代价和能力边界是什么。

比较替代方案时只讨论对理解当前设计真正重要的方案，不堆砌无关架构或假想风险。

### 6.2 用具体数据解释抽象行为

尽量通过真实业务数据和可观察状态帮助理解。

例如：

- 玩家等级、装备、金币怎样变化。
- 两个协程分别执行到哪里。
- 消息在什么时刻进入队列。
- 一张 table 被谁引用。
- 原对象与新对象是否相同。
- 一份状态快照在什么时刻创建和释放。

对复杂机制，可以提供状态表、对象引用关系图、事件时间线或调用链图。

### 6.3 解释对象和状态的生命周期

对于涉及状态、缓存、快照或引用的模块，必须跟踪关键对象：

- 何时创建。
- 由谁持有。
- 何时被读取或修改。
- 是否改变对象身份。
- 何时释放。
- 失败时保留什么。
- 哪些副作用无法自动撤销。

不能仅凭“更新成功”“恢复成功”等概括跳过关键状态变化。

### 6.4 利用学习者已有的工程经验

当新机制与熟悉的架构具有可比性时，应主动建立对照。

例如讲解 Skynet，可适当联系传统 C++ MMO 服务端中的 Gateway、GameServer、网络消息分发、业务线程、异步任务和玩家状态管理。

对照必须说明相似点和本质差异，尤其不能因为名称相似就认定并发、隔离和生命周期语义相同。

跨技术栈教学时，优先使用学习者熟悉的真实工程背景降低理解成本。

## 七、完整课程必须独立、自洽

课程应以首次接触目标模块的学习者也能独立完成为标准。

即使学习者有丰富的编程经验，也不能默认其了解当前框架特有的接口、生命周期、消息协议或内部约定。

首次出现的重要概念必须解释到足以理解当前代码。

不能使用以下方式回避必要内容：

- “这个在上一课讲过。”
- “这一点以后再介绍。”
- “这里暂时不需要知道调用关系。”
- “该函数具体怎么执行不重要。”
- “参考官方文档自行配置。”

如果属于当前完整链路必不可少的知识，就应在当前课程中讲清楚。

允许引用官方资料作为补充，但不得把它作为完成课程的必要前置阅读。

课程章节数量应按真实学习需求确定，不强行拆课，也不为了合并而压缩重要内容。

一门完整课程结束后，应能够基本结束该模块的系统性学习，而不是仍需依靠大量后续补课才能建立全局理解。

## 八、真实源码和版本必须严格核对

编写教程前必须读取：

- 项目适用的 AGENTS.md 与工程 Skill。
- 当前指定分支、提交和相关版本信息。
- 目标模块真实源码。
- 上下游调用方。
- 相关配置、协议和依赖。
- 已有测试与真实运行示例。
- 与本课程直接相关的工程文档。

例如讲 Skynet 时，应确认实际使用的 Skynet、Lua 版本以及是否有工程改造，不能默认其行为与官方版本完全相同。

真实源码讲解必须与指定代码基线一致。

严格区分：

1. **源码事实**：已由具体实现确认。
2. **运行验证**：已通过实际执行和输出确认。
3. **原理推导**：根据源码能够推导，但未实际运行验证。
4. **设计建议**：属于改进意见，并非当前实现。

不能虚构接口、调用关系、错误码或运行结果。

旧课程可以帮助了解教学历史，但不能代替最新源码核对。

发现源码、文档、测试之间存在实质矛盾时，应明确指出，不得靠自行假设填补。

## 九、按阶段实施并验收

每个阶段采用统一教学节奏：

**本阶段背景 → 当前工程状态 → 具体问题 → 实施目标 → 创建或修改代码 → 运行操作 → 观察结果 → 深入源码 → 解释机制 → 阶段总结 → 衔接下一阶段。**

每个重要阶段至少应提供：

1. 当前已完成的工程内容。
2. 本阶段新增的功能或实验目标。
3. 需要编写的文件和代码。
4. 实际运行命令。
5. 预期输出和关键观察项。
6. 结果为什么会这样。
7. 异常时的排查入口。
8. 本阶段结束后工程应处于什么状态。

测试应尽早进行，不要在没有验证的情况下不断堆积代码。

运行命令必须符合实际目录和工具环境。

预期输出可以根据源码推导，但必须标明是预期结果；只有真实执行成功后才能声明测试通过。

## 十、正常流程、异常流程和工程维护形成闭环

根据模块特性，课程应覆盖必要的：

- 初始化与启动。
- 正常业务流程。
- 核心功能与内部协作。
- 并发及生命周期问题。
- 典型错误和失败路径。
- 恢复或后续修复机制。
- 测试、日志、排查和维护。

### 故障实验要求

故障案例应基于真实机制设计，而非仅描述假设。

必须说明：

1. 故障注入位置。
2. 为什么会触发。
3. 影响哪个组件、对象或执行阶段。
4. 当前执行链路如何进入失败分支。
5. 已经发生了哪些状态变化。
6. 哪些状态成功恢复、哪些仍然保留。
7. 后续应如何验证或修复。

每个故障实验必须具有明确的初始条件，避免前面实验的内存状态、缓存或文件修改污染后续实验。

对于支持后续修复的模块，应根据真实设计演示如何从当前实际状态继续修复，而不是默认所有系统都必须回滚、锁定或人工确认。

不能把特定架构的故障处理偏好强加给其他模块。

## 十一、保持教学 Sample 简单，但不能牺牲真实性

教学 Sample 是为了观察和理解目标机制。

优先采用最小且足够真实的实现，不为了教学增加大量不相关功能、包装层、辅助管理器或复杂工程结构。

同样，不应为了让 Sample 看起来简单，就绕过目标模块的实际接口或使用不具备真实行为的伪实现。

必要的工程配置、启动流程、状态管理和错误处理必须保留。

**案例简单，机制解释深入。**

## 十二、明确教学边界和执行权限

教学与工程改造必须区分。

- 教程可以读取、分析和解释真实源码。
- 教学 Sample 由学习者按步骤亲手实现。
- 未经授权，不得修改真实框架源码或改变现有架构。
- 如果教学案例需要当前模块不支持的能力，必须先说明限制，不得虚构接口。
- 如果出现需要修改既有工程合同的情况，必须先与学习者确认。
- 不擅自扩张课程目标，不一次提出大量无关备选架构。
- 未经明确要求，不直接生成课程文件、提交代码或修改仓库。

当用户只要求课程设计时，仅输出教学方案；当用户明确要求开始编写时，再交付正式课程内容。

## 十三、课程结构与交付要求

完整课程应先设计总体方案，确定：

- 真实业务背景。
- 核心学习目标。
- 独立 Sample 的功能范围。
- 从零实施的先后顺序。
- 贯穿始终的主要对象和数据。
- 完整执行调用链。
- 哪些源码是必须深入讲解的重点。
- 每个阶段的实验与验收条件。
- 故障场景及最终综合验收。

正式教程按该方案连续展开。

篇幅较长时可以分章节交付，但必须保证最终内容属于同一套完整、连续、可执行的教学工程。

不能因为分章节输出，就丢失已有工程状态、反复从头讲解，或者要求学习者自行拼接不同章节的代码。

## 十四、最终验收标准

正式交付前逐项检查：

1. 是否从真实工程问题出发，而不是从抽象 API 开始？
2. 是否使用一套独立、真实、可运行的 Sample？
3. 学习者能否从空教学目录按步骤亲手实现？
4. 所有文件、代码、依赖、配置和运行命令是否完整？
5. 是否始终维持一条连续的业务故事线和真实执行调用链？
6. 每段重要源码是否交代文件、函数、调用者、参数、执行背景和后续去向？
7. 大函数拆分是否连续，跨文件或跨协程是否交代清楚？
8. 重要机制是否通过具体例子、状态变化和真实源码讲透？
