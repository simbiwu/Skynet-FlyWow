# 工程合同与最小设计补充规范

本文件补充现有 Coding Standard，不替代其中的 API、返回合同、状态和最小实现规则。若出现冲突，以 AGENTS.md、用户确认合同和 Coding Standard 的明确规则为准。

## 合同核对

代码修改前识别受影响的可观察合同：公开 API、参数/返回、多返回值、错误码和抛错、协议字段、状态 owner、生命周期、调用顺序、失败行为和外部副作用。内部实现说明不自动等于公开合同。

未经用户明确授权，不改变上述合同。测试通过不能代替合同变更授权。

## 技术事实与约束来源

每个技术限制、常量、配置上限、时间范围、状态和防御机制，都必须能追溯到以下至少一种真实依据：

- 用户明确提出的业务要求；
- 已确认的公开 API、协议或模块合同；
- 项目实际使用版本的第三方公开 API 或源码行为；
- 已证实的生产调用路径和运行时约束。

不能仅根据第三方库的内部字段、实现细节、旧注释、测试构造或理论风险推导业务限制。必须检查公开 API 的完整返回路径及跨语言 Binding；内部类型与对外类型可能不同。

无法确认依据时，标记为待核实，不得先把它做成公共常量、配置上限或业务合同。

## 常量与公共模块归属

同一个数值出现在多个地方，不代表它们具有相同语义；同一个底层限制被多个模块引用，也不代表它属于 `common`。

常量应由真正拥有该业务规则或稳定技术合同的模块定义。只有多个真实消费者共同依赖同一项稳定语义，且存在明确 owner 时，才提取到公共模块。

不得把某个模块的实现细节或第三方库内部限制提升为跨模块的业务配置规则。公共模块只提供稳定、可复用的能力，不替调用方决定其业务策略。

## 复杂度必要性

新增或保留类、接口、状态、配置、包装层、转换、校验、断言、Fallback 和恢复机制时，说明它解决的当前真实问题。不能只用未来扩展、代码风格、已有引用或理论风险作为理由。

优先采用现有机制和直接调用。一个简单流程不为了形式统一拆成多层对象；一个事实不重复存储；一个语义对象不在每层换名包装。

## 状态与 owner

每个需要持久保存的状态都应能说明：

- 表示的业务事实；
- 唯一 owner；
- 创建、更新和失效时机；
- 真实生产消费者；
- 消费者据此采取的决策；
- 是否可从权威状态派生。

若无法指出真实消费者和决策，优先考虑删除或派生。

## 保护机制

每项检查、断言、同步和恢复机制都要指出保护对象、触发边界、可达事件及失败后果。不要将函数层级当作信任边界。已在可信边界验证且未被修改的条件，不在每个内部调用重复验证。

跨越新的不可信输入边界、数据被修改、授权关系变化、跨 yield 后身份可能失效或共享状态并发变化时，重新评估相关检查。是否需要重验必须由真实失效路径决定，不机械地在每次 yield 后重复检查所有字段。

## 设计验收

审查完整流程，而非孤立函数。对可疑结构提出直接替代方案，并同时核对新方案下必要的安全、并发、资源和公开合同保证。
