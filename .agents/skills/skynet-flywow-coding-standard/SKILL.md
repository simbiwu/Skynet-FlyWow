# Skynet-FlyWow 编码规范

本 Skill 负责代码层面的统一规则。项目边界、需求边界和修改权限以根目录 `AGENTS.md` 为最高项目规则。

## 修改前

先确认三件事：

1. 当前任务明确要求什么。
2. 为完成这些要求，哪些工程处理是必需的。
3. 哪些只是额外增强。

只实现前两类。第三类只建议，不直接实现。

不要因为代码“以后可能会用”而增加抽象、配置、状态、目录或接口。

## 排版

FlyWow 使用一致、可读的排版。

### C/C++

使用 Allman 风格：

```cpp
if (ready)
{
    Run();
}
```

类、函数、命名空间和控制块保持一致。

### Lua / Proto / 配置

多行具名 table、record、message 保持清晰缩进。属于同一小组的字段可以对齐，但不要跨不相关代码强行排版。

例如：

```lua
local state =
{
    phase    = "created",
    config   = nil,
    registry = nil,
}
```

不要为了满足格式规则把多条独立语句挤到同一行。

### 逻辑分段与可读性

- 一个函数内有多个阶段时，阶段间用空行分隔，并在每个重要阶段开始处用简短中文注释说明目标、关键状态变化或边界条件。阶段不显然时，不要只在前一阶段结尾补笼统说明。注释只标出真实流程边界；简单连续步骤或代码已清楚表达的分组只用空行，不为每个空行加标题，也不重复翻译代码。
- Lua 空行按逻辑阶段和语义关系判断，不因前一条语句以 `end` 结束或代码缩进回到同级就自动插入。连续完成同一小步骤的语句保持在同一段；同一组状态声明、table 字段和表达式续行也保持紧凑，不在每条语句之间机械插入空行。
- 函数拆分以降低整体阅读成本为准，不以行数作为硬性条件。即使超过 20 行，只要流程连续、逻辑清晰，也可以保留；优先用空行分隔阶段。只有明显降低理解成本、形成真实复用，或隔离独立复杂逻辑和资源生命周期时才拆分。禁止为缩短函数而机械拆分。
- 空行只表达逻辑边界；连续代码块必须属于同一不变量或同一资源生命周期。
- 长函数无法快速呈现输入、状态变化、核心算法和输出边界时，属于可读性未完成，不能仅因编译和测试通过而交付。

例如，前一段完成参数检查，下一段准备候选并进入核心处理时，应分开；elseif 仍与原分支结构放在一起：

~~~lua
if not request then
    return result.failure("HU_INVALID_REQUEST")
end

local candidate = prepare(request)
if not candidate then
    return result.failure("HU_PREPARE_FAILED")
end

commit(candidate)
return result.success()
~~~

## 注释

注释的目标是降低阅读成本，不是增加合同数量。

### 注释交付门禁（强制）

每次新增或实质修改源码后，必须对本次涉及的非平凡函数逐个审查，不得抽查或只修改一两个代表函数。判断标准如下：

1. **函数职责**：公开 API、模块入口及非平凡函数，必须有紧邻函数的中文职责说明，使读者知道它负责什么，以及理解它所必需的调用时机或约束。简单且完全自解释的 getter、谓词和单步包装函数可以省略。
2. **重要变量与数据结构**：业务状态、跨函数传递的 record、模块长期状态，以及多个用途不同的集合，必须在声明处或紧邻处说明业务含义、数据来源和后续用途。根据实际情况补充 owner、生命周期、写入者、读取者、单位、哨兵值及失败后果。
3. **函数内部阶段**：包含多个处理阶段、状态迁移、复杂判断、数据转换、资源生命周期、并发处理或错误恢复的函数，必须在关键阶段开始处说明该阶段的目的、重要状态变化和约束。函数头注释不能替代内部阶段注释。
4. **数据流与集合区别**：同一函数维护多个不同用途的集合、record 或快照时，必须说明它们分别保存什么、为什么需要区分，以及后续在哪个阶段使用。不得要求读者仅通过追踪所有赋值和调用点自行猜测。
5. **非显然操作**：编译与执行的区别、缓存或快照的用途、失败后是否回滚、yield 前后的状态有效性、资源归属和清理时机等，只要不能从局部代码直接看清，就必须在相邻处说明。
6. **有效性判断**：注释必须提供源码本身无法直接表达的信息，例如原因、约束、数据含义和阶段目标。只写“处理数据”“检查状态”“更新模块”等空泛标签，不算完成；只复述变量名、类型或下一行代码，也不算完成。

这是一项代码交付要求，不是注释数量竞赛。不得为了通过检查而给每个简单变量、赋值、判断或循环机械添加注释。若代码与注释仍然让维护者无法理解关键变量或流程，必须继续改善命名、注释或必要的代码组织。


### 必须写清楚的地方

以下位置需要完整或足够明确的合同：

- 公开 API；
- 跨模块边界；
- 跨 Service 消息；
- ownership 或生命周期不直观；
- 会 yield、I/O、加锁或修改共享状态；
- 并发约束；
- 失败语义不明显；
- 协议、字节布局、坐标、单位、版本或算法不变量。

根据实际需要说明参数、返回、失败、ownership、单位、yield/I/O 等信息，不要求机械凑齐固定字段。

FlyWow 自有代码的注释要求覆盖所有模块和功能领域。关键规则、数据关系、公式、单位转换、阈值、固定数值和状态变化若不能从局部名称与语法直接理解，应在相邻处说明其含义、单位/边界及数值来源（模块配置、Contract 或当前实现约定）。原因或来源不清时先核查模块配置、Contract 和调用链，不得编造；简单直观的语句不逐行注释。

### 简单内部函数

简单辅助函数只写真正有帮助的注释。

能从函数名和代码直接看懂的内容不要重复解释。

禁止：

- 把源码注释写成教程；
- 逐行翻译代码；
- 每个函数机械重复“参数/返回/ownership/I/O/yield/复杂度”；
- 为显而易见的赋值、判断、RAII 或普通循环写大段说明；
- 用注释数量证明代码“商业级”。

注释优先解释：

```text
WHY
重要约束
非显然行为
容易踩坑的生命周期或并发边界
```

不直观的公式、坐标换算、插值、索引映射可以给一个短例子；简单代码不要硬加例子。

- 变量、配置字段和回调的注释不能只换一种说法复述名称或类型，也不能只贴“状态”“安全条件”“检查结果”等空泛标签。应说明它在当前流程中代表什么、由谁或何时读取/更新，以及取值或变化影响哪一步；按需补充来源、单位、owner/生命周期、默认值原因、哨兵值和失败后果。名称、类型及邻近代码已能说明的短期局部量不写重复注释。
- 跨模块或跨多个流程阶段共享的变量/状态，必须在声明处或紧邻的集中定义处说明业务含义、owner/生命周期、由哪些模块或阶段写入和读取，以及状态变化如何推进流程；不得要求读者只能靠追踪完整调用链推断。

项目自有、手写 C++ `struct` 中的每个字段都必须就近注释，说明它在该结构中的业务职责；字段名直观也不能省略。注释不得只复述字段名或类型，应说明字段在整体记录中的作用，并按需写清来源、单位、合法值/哨兵值、状态变化和序列化含义。字段注释优先使用行尾 Doxygen 兼容的 `///<`，长说明可写在字段声明正上方。生成文件和第三方代码不适用。

- 同一逻辑组内声明多个相关状态变量时，每个变量必须单独占一行，且每项声明都必须带行尾注释，
  不得因为名称直观而省略。按列对齐变量名、赋值符和行尾注释标记；所有行的 `--` 与注释正文
  起始列一致，使用空格补齐、不用 Tab。注释说明该变量在组内的职责，以及名称无法表达的 owner、
  来源或生命周期，不得只复述变量名。长说明仍须保留行尾简注，详细内容可另写在定义前；前置说明
  不得替代行尾注释。只对齐同一组连续声明，不跨空行或无关逻辑。Lua 多行具名 table 的字段若带
  行尾注释，也按列对齐字段名、赋值符和注释标记。

例如：

```lua
local service_runtime     -- 当前 Lua State 的热更 Runtime；在注册 RPC 前创建，持有本地控制状态。
local declared_modules    -- 本 State 通过 M.require 声明可参与受控模块更新的模块名集合。
local service_guard       -- 当前 Service 的 Guard；注册前创建时由 Runtime 复用。
local local_module_engine -- 未注册 Service 使用的本地模块更新器。
```


同一个手写 C++ `struct` 的全部字段作为一个对齐范围，包括空行分组之间的字段；字段名、赋值符和行尾 `///<` 注释标记分别按列对齐。不同字段类型通过类型后的空格完成对齐，不得改变字段类型、顺序或初始化值。对齐范围不跨越不同的 `struct`。

## 命名规则

- C++ 类型（class、struct、enum、type alias）使用 PascalCase；自由函数和成员函数使用 lowerCamelCase；命名空间、局部变量、参数和普通变量使用 snake_case；类私有成员使用 snake_case_；具有固定程序期值的常量及枚举项使用 kPascalCase；宏使用带项目名前缀的 UPPER_SNAKE_CASE；C++ 源文件使用小写 snake_case。
- Lua 脚本中的函数、局部变量、参数、模块字段和普通 record 字段使用 snake_case；常量使用 UPPER_SNAKE_CASE；LuaDoc 类型名使用 PascalCase。
- Lua 文件级声明集中放在文件开头：依赖之后先定义文件级常量，再定义模块导出表 M、私有 module_state（确有多个共享可变状态时）以及核心类型/原型表和紧邻的 __index。这些主体声明不得排到私有辅助函数之后，也不因“靠近使用处”而移动。每个实例的可变状态仍放在该实例自己的 record 中；函数内短期局部量和按调用创建的 record 继续靠近其使用位置。
- 模块长期持有的可变状态字段应在文件开头的模块状态表中集中声明，并就近逐项注释其职责、owner、何时更新及影响的流程。若模块已明确采用模块表本身作为唯一单例状态对象（例如单实例 Controller），沿用该表；若公开模块表 M 与私有状态分离，则私有字段仍放在 module_state，不挂到 M。配置或初始化结果决定的字段可以先声明为 nil，只有全部校验成功后才统一赋值；运行时处理可以更新已声明字段，不应在分散的处理分支中首次创建模块长期状态字段。请求级、批次级等短期 record 的字段仍在 record 创建处定义，不要求重复列到文件头。
- 名称的具体程度应随作用范围和生命周期增加。模块方法、模块级状态字段、跨函数共享对象及长调用链中的 record，使用简短且能说明职责或对象的名称；避免单独使用必须依赖上下文猜测的泛名，例如方法名 `run`、`load`，或保存具体批次记录却只叫 `active`、`last` 的字段。名称具体不等于堆叠内部步骤，不为追求具体而写成长句。稳定 API、协议命令和已有术语遵守现有合同。除语义确实通用外，不用 `options`、`args`、`values`、`data` 等泛称代替可明确命名的对象；短期且紧邻使用的局部量可按实际语义使用简短名称。
- 一个模块有多项由其 API/函数共享的可变运行状态时，可集中在文件私有的 `module_state` 表中；不得把这类私有运行状态挂到返回给调用方的 `M` 表。表字段仍使用具体名称，`module_state` 不能成为使用泛称字段的理由。单个简单状态不为套用规则而额外建表。
- 避免参数或局部变量遮蔽外层绑定，尤其不得用同名参数/局部变量遮蔽模块状态。同一层次不同语义的对象不能复用同一个含混名称。
Lua 对外模块入口、Service 名和文件名遵守 FlyWow 已有命名合同。
- Lua 可见的公开字段和函数名使用 snake_case。
- 新增或本次任务修改的、直接注册为 Lua 模块函数或 userdata 方法的 C++ Binding 回调，函数标识符必须与 Lua 可见名称逐字符一致（包含大小写和下划线），注册语句也使用同名标识，例如 `module.setFunction("preload", preload)`、`methods.setFunction("step_frame", step_frame)`。这是对 C++ 自由函数和成员函数 `lowerCamelCase` 规则的窄范围例外；命名冲突时通过命名空间限定，不改回调名。
- 此约束只作用于直接注册给 Lua 的回调，不约束其内部 C++ 辅助函数；辅助函数继续遵循 C++ 命名规则。已有 Lua API 保持公开名称不变；修改对应 Binding 时，通过调整 C++ 回调标识符实现名称一致。
- luaopen_* 等 C ABI 符号遵守 Lua 加载合同。稳定协议字段、配置键或历史公开合同按其格式约定，不为统一代码风格而擅自重命名。
- 新代码统一按以上规则编写；修改旧代码时只整理当前任务涉及的标识符，并同步受影响的调用点，不借规则进行全仓批量改名。

### 调用边界中的语义对应

- 同一业务对象或 record 在连续调用、转发、保存和返回过程中，应沿用同一个领域化名称。不得只因跨函数或跨模块，就将同一个对象从 `service_registration` 改称 `options`、`args`、`values` 等泛称或同义词；名称必须在生产者、形参、局部变量和消费者之间保持可追溯。
- `options`、`args`、`values`、`data` 等通用名称，只用于语义本身确实通用且不存在更具体领域名称的对象，例如任意位置参数集合、多个返回值序列或原始字节数据。不能把它们作为同一具体对象在调用链中的轮换名称。
- 对象经过解码、筛选、重建、复制或汇总而形成了不同语义对象时，应使用新名称，并在转换处清楚表达输入与输出关系。例如 `payload` 字节解码成 `envelope`，再从中取出 `request`；同一个 `route` record 原样转发多层时则保持 `route`。
- 这条原则适用于普通函数、回调、异步 RPC、Service 转发和跨语言调用。Binding 仍遵守上方更具体的规则：表达同一个 Lua 公开操作的 C++ 回调名与 Lua 名称逐字符一致。
- 稳定 API、框架合同和协议字段不因本规则被擅自改名；整理旧代码时只改当前任务涉及的名称，并同步调用点，不借此规则批量重命名。

例如，形参 `name` 能直接对应调用处传入的 `name`；无语义的 `arg1` 会让读者额外记映射关系。相反，若字节串经过解码成为请求对象，名称变化是在说明语义变化，应使用能表达新对象的名称。

```cpp
std::uint32_t map_id      = 0; // 请求指定的地图 ID；0 由上层合同判为无效。
std::uint32_t map_version = 0; // 与 map_id 配对的不可变地图版本。
```

```lua
local state =
{
    map_id      = map_id,
    map_version = map_version,
}
```

## IDE 可读的注释

- C++ 公开类型和 API 使用 Doxygen 兼容的 /// 注释及 @param、@return、@note 等标准标签，使 clangd、Visual Studio 等 IDE 能在悬浮提示中显示合同。中文说明写清语义、失败与 ownership；不要求额外引入 Doxygen 文档生成器。
- C++ 实现内部使用普通 // 或块注释解释局部 WHY、栈变化和资源边界；这些注释贴近对应操作，不用 @param 等 API 标签，也不重复公开声明中的合同。
- Lua 源码使用 Lua Language Server 可识别的 LuaDoc/EmmyLua 标准标签；注释与结构化类型只维护一份，避免 IDE 看不到的自定义标签及重复普通注释。
- LuaDoc 类型声明应靠近所属 API；被多个 API 共用时再集中定义。只服务一个 API 的 class/alias 及字段说明应紧邻该 API 的参数和返回注释。配置字段和回调字段要解释调用时机、触发条件、返回值含义及失败后果；不能只写“附加条件”或“检查函数”等空泛说明。
- 注释要适配 IDE 的源码解析：标签写在其所描述的声明之前，避免把 API 合同只写在调用点、Markdown 或无法识别的自定义格式中。

## 文件头

公开模块入口、复杂 Runtime 文件、跨语言 Binding、重要 Build/Test 脚本可以在文件头简要说明职责和边界。

简单源码、测试辅助文件、很短的构建文件不强制写固定五段式文件头。

文件头不得大段重复 README、Contract 或函数注释。

## Lua 与 Skynet

- 稳定公开 Lua API 优先使用明确参数或 request/result record。
- 为兼容已有稳定 API（例如 `skynet.error(...)`）可以使用 `...`，并在附近说明原因。
- 可能 yield 的入口必须让调用者能判断这一点。
- 不跨 yield 保存未经重新验证的连接身份、fd、borrowed buffer 或临时状态。
- Service handle 优先显式传入，不因为“方便”增加全局 Service 名称。
- 数据平面不得无理由从 `send` 改为 `call`。
- 不把日志文本作为业务返回协议。

## Native C/C++

- ownership 必须能从类型、成员关系或必要注释中看清。
- 多个 Skynet Service 可能在不同 OS Thread 调用 Native 模块时，mutable process-global 状态必须有明确同步或禁止共享。
- 不为了“线程安全”给确定为单 owner 的状态额外加锁。
- C ABI / Lua C API 边界不得让 C++ exception 穿出。
- Lua C API 中涉及 userdata、GC、longjmp、栈平衡时，必须说明非显然的资源边界。
- Lua C API 封装内部对关键栈操作写详细中文注释：说明操作前后栈形态、正/负索引、压入/消耗/保留的值、raw 访问与元方法的区别、lua_next 迭代时 key/value 的处理，以及错误和异常路径如何恢复栈。
- 涉及 luaL_ref/luaL_unref、closure/upvalue、metatable、placement-new 和 __gc 时，注释说明引用 owner、释放时机、构造/析构状态与内存责任。集中实现处解释机制，调用点只解释特定业务约束，不逐行翻译 API。
- 高频路径避免无必要的临时分配、全局锁和跨 Service 同步等待。

## API 与实现

### 函数返回合同与 LuaDoc

- 公共类型与构造器定义在 common/lualib/flywow_result.lua，Lua 模块通过 require "flywow_result" 使用。项目自有 Lua 模块中，可预期的业务或运行失败使用 FlyWowResult<T>：成功为 {ok=true,value=...}，失败为 {ok=false,code=...,message=...,details?=...}。调用方先检查 ok，再读取 value 或失败字段。
- FlyWowResult 的公共顶层字段保持通用。模块专属成功数据放进 value，模块专属失败诊断放进 details；错误码由所属模块定义，message 不作为机器协议。
- 纯计算 helper、无失败可能的简单操作可以返回其自然值或不返回值，不为套用结果合同额外包装。
- 明确适配 Lua/Skynet 原生调用习惯的入口可以保留原合同；必须在公开 API 注释中写明成功返回、失败方式、可能的 yield。适配实现不应把原生异常格式传播给框架内部控制协议。
- pcall 的布尔值和异常值只在异常捕获边界使用；变量名应表达执行状态或异常。跨模块/API 边界前转换为约定结果，不传播自定义的 nil,error、value,error 混合格式。
- 每个具名函数都必须有 LuaDoc @return。无返回值写 @return nil；多个返回值按顺序分别标注类型和名称；联合或可空返回必须覆盖所有分支及其含义。返回结果表时写明具体类型、成功载荷和失败语义，不能只写笼统的 table。
- @return 说明静态返回合同；函数说明还须标明可能 yield、抛出异常或执行 I/O 的行为。

- 同一语义的数值约束被多个模块或多个位置引用时，应定义在所属模块的公共常量中，由检查、边界处理和错误信息统一引用；不要散落重复数字。职责不同的限制即使当前数值相同，也必须分别定义。跨语言边界若无法直接共享定义，应保留各语言所属模块的定义并明确其对应关系，不为消除数字重复额外引入生成或运行时抽象。
- 模块依赖保持单向。
- 框架核心不得引用宿主项目 DTO、Battle/SLG 业务类型或开发机路径。
- 公共 API 保持小而稳定。
- 错误结果必须让调用者可以程序化判断，不依赖解析日志字符串。
- 配置在边界校验，内部代码可以依赖已经建立的不变量。
- 当前功能实际拥有的资源和状态必须有明确 owner 与释放路径。
- 只有会实际积累、耗尽或失控的资源，才需要对应容量或过载策略。

不得因为本 Skill 提到资源、失败、商业级或可维护性，就主动新增：

```text

重试
缓存
采样
metrics

后台任务
队列
熔断/降级
插件系统
未来扩展点
```

这些只有在当前需求明确需要，或正常运行无法缺少时才实现。

## 抽象与函数拆分

优先选择当前问题最直接、最容易阅读的实现。

不要机械按“单一职责”把一个连续逻辑拆成大量小函数。

以下情况才值得抽函数或类型：

- 逻辑有独立名称和稳定含义；
- 被真实复用；
- 能明显减少主流程认知负担；
- 需要隔离资源、生命周期或测试边界。

新增 `Manager`、`Factory`、`Provider`、`Context`、`Adapter`、`Wrapper` 等类型前，必须能说明它解决的当前真实问题。名称本身不是设计价值。

### 最小实现优先原则

1. 优先使用现有 API、类型和代码结构。标准库或项目已有能力能够解决的，不再无意义地包装。
2. 保持主流程直观。参数检查、核心处理、错误处理和结果返回可以放在一个函数中；不要让阅读者为了理解一个简单操作反复跳转 Helper。
3. 不为假想需求引入接口、Factory、Provider、Adapter、插件点或配置；只有真实消费者和当前需求才能证明新增抽象的价值。
4. 每项输入事实在首次接收它的可信边界校验，并把已验证合同传给下游；下游只检查自己才能观察的本地状态，或跨 yield、RPC 等阶段可能变化的不变量。仅经 RPC 传递本身不意味着字段值或格式需要重验；若来源受信且发送方从已校验状态固定生成请求，接收方沿用该合同。授权来源、许可/批次身份关系及接收方本地状态仍按其自身不变量检查。不得重复校验调用方刚确认且中间未改变的同一条件，也不得让字段写入 Helper 重复检查调用方已验证的前置条件。删除检查前沿生产者、传递路径和消费者确认数据不可绕过、未被改写且校验结果确实传递；整批写入前统一核验与恢复时逐项核验属于不同安全阶段，应保留。
5. 新增类型、Helper 或间接层必须能证明它比直接实现更容易理解和维护。仅转移代码位置、没有独立价值的封装不保留。
6. 实现完成后主动复查：删除无价值的单次调用 Helper、重复检查、冗余状态和没有消费者的扩展接口；只删除确认无价值的代码，不牺牲正确性和必要的测试。
