# 代码审计与复杂度审计

## 适用范围

用户要求完整模块审计、提交 Review、复杂度审计、最小化审计或整改清单时使用。

普通提交 Review 以变更范围为主；用户明确要求完整模块审计时，沿真实生产入口检查完整相关实现，不得只看 diff。

## 1. 确定审计基线和证据

审计前确认仓库、分支、commit、工作区状态及项目实际使用的依赖版本。区分本次 diff 与原有实现，避免把历史问题误报成本次引入，也不能因问题不在 diff 中就忽略用户明确要求的完整模块审计。

涉及第三方 API、运行时、编译器、Lua Binding 或框架调度时，核对当前项目实际使用版本的源码和公开合同。不得只引用最新版文档、函数名称、内部字段或 AI 先前结论。

对每个关键结论说明证据类型：

- **源码事实**：代码位置、API 实现或公开合同；
- **调用链事实**：生产入口、调用者、调用顺序、数据流和状态变化；
- **运行验证**：实际执行的测试、场景或命令；
- **测量结果**：benchmark、profiling、延迟或资源数据；
- **推导/待证实**：基于源码的推导，或目前缺少证据的判断。

不能把推导写成实测，也不能把尚未证实的假设写成缺陷。

## 2. 用户目标与审计范围门禁

先提取用户要求的效果、明确排除项和适用合同。只对这些目标和合同作符合性判断；不能用未被要求的性能优化、过载处理、通用健壮性或行业惯例替换用户目标。

每个发现须同时满足“有证据”和“与当前审计目标相关”才可列为本次整改项：

- **规则/合同违反**：指出适用条款和当前实现违反它的证据；
- **已证实缺陷**：指出受支持的生产路径、触发条件和实际错误后果；
- **最小化/复杂度问题**：指出具体冗余结构，并给出满足同一目标与合同的更简单实现；
- **可选改进/范围外观察**：有潜在收益或风险，但没有证明当前目标或合同因此不成立。

可选建议不得包装成缺陷、严重级别、必改清单或验收条件。用户要求按审计结果实施或“完整收口”，只授权修复已成立且属于当前范围的发现。证据不足标为“尚未证实”。

新增容量限制、限流、背压、断连、丢弃、重试、降级、恢复等会改变运行行为的策略，只有当前目标/合同明确要求且证据证明其必要时，才能列为必改。否则作为可选方向说明收益、成本和行为影响，不自行实施。

## 3. 三个审查维度

### 合同与需求符合性

检查功能是否满足原始需求，是否遗漏要求、改变可观察行为或扩大范围。区分公开合同、内部实现说明、历史记录和测试实现。

### 工程正确性

检查真实数据流、控制流、错误传播、并发、yield、资源 owner、生命周期、边界验证和必要测试。只报告有代码证据的风险。

### 设计必要性

主动寻找可以删除、合并、简化或替换的结构。不能只判断现有设计是否自洽；必须独立推导满足同一目标的更简单完整实现。

## 4. 必查的复杂度来源

- 多余的 Manager、Controller、Helper、Wrapper、Adapter、Provider、Factory、Context；
- 无独立职责的转发层和过长调用链；
- 同一事实的多个状态变量或多个 owner；
- 同一语义数据反复复制、包装、转换、换名和透传；
- 沿调用链重复执行的相同校验、断言、错误转换和 Fallback；
- 由内部对象或中间层引入的生命周期、清理、同步和恢复机制；
- 没有当前消费者的配置、策略、扩展点和通用接口；
- 只为旧内部实现服务的测试、样例和文档；
- 为理论上不可达的事件增加的去重字段、阶段门禁和防御状态；
- 没有业务或公开合同依据、仅从底层实现细节推导出的常量、上限、状态和配置约束。

## 5. 技术假设与底层合同审计

每当实现依赖某个技术前提，必须追到实际来源：

1. 确认项目使用的准确版本、分支或 commit。
2. 检查公开 API 的实际实现和语言 Binding，不能只看内部数据结构。
3. 确认参数和返回值经过 C/C++、Lua 或其他语言边界时的类型转换。
4. 确认单位、精度、范围、溢出、回绕、取消、yield 和线程语义。
5. 对照真实生产调用链，确认该限制是否会影响调用者的实际行为。

最小设计必须基于实际工程运行机制、资源所有权、调用时序及错误后果独立判断。Sample、宿主调用和测试只是参考证据，不得仅凭其覆盖范围决定机制是否必要。保护机制能够处理某种情况，不代表有保留价值；新增复杂度必须证明当前工程收益，不得仅以理论风险或提高健壮性为理由实施。

## 6. 性能与并发审计

性能问题先还原真实执行拓扑，不用“异步 IO”“协程”“多线程”这些词直接推断并行能力。

对 Skynet 至少确认：

- 代码运行在哪个 Service、Lua State 和协程；
- Service 消息队列如何调度；
- 当前函数是否会 yield，yield 前后的执行关系；
- 同一 Service 的 Lua 代码是否串行执行；
- Worker Thread 能否并行处理不同 Service；
- CPU 计算、全量扫描、编解码和回调实际在哪里执行；
- 异步 Socket IO 解决了什么等待，是否真的让 Lua 业务代码并行。

同一 Service 内的 Lua 协程通过 yield 交错执行，不等于多核并行；异步 IO 也不会自动把同一 Service 的 CPU 工作分摊到多个核。不得把“连接一协程”误判成“每连接一个线程”。

对无 yield 的 O(N) 全量扫描，可以直接从调用路径和复杂度判断它会连续占用该 Service 的执行时间，并延迟同 Service 后续消息；证明这一结构性事实不需要先做 benchmark。若要量化吞吐、p99 延迟、CPU 占用或确定阈值，则必须使用实际测量，不能凭源码编造数字。

反过来，也不能仅凭理论复杂度就宣称某个实现已经造成特定线上延迟。区分结构性影响、实际观测和待测量影响。

## 7. 测试有效性审计

- 检查测试实际执行的命令、CI Job 和退出结果；测试文件存在不等于测试已运行。
- 测试既要验证业务行为，也要验证影响方案的关键技术前提。
- 不要让测试只验证内部 Helper、历史调用顺序或一个未经核实的设计假设。
- 测试可以构造边界值，但该边界必须对应真实数据类型、公开合同或业务需求。
- 测试通过只能证明被执行的断言通过，不能证明整个设计合理。
- 删除内部结构时，评估测试是否应改为验证外部行为；公开合同测试不得擅自删除。
- 未执行、被 skip 或无法在当前环境执行的测试，明确标记为 `not verified`。

## 8. 重复防御审查

沿完整调用链定位每项验证的责任边界：

1. 找到数据第一次进入系统的位置。
2. 确认该处是否为不可信边界，以及实际验证了哪些条件。
3. 跟踪数据是否被修改、重新解析、跨越新的信任边界或经历可能改变有效性的 yield/RPC。
4. 对每次重复检查说明它独有的风险和决策用途。
5. 没有新边界、数据未变且不变量仍成立时，重复检查通常应删除或集中到唯一责任点。
6. 不同检查若分别验证格式、授权、接收方本地状态或跨 yield 后身份有效性，不得因表面相似而合并。

状态、数据和错误也按同样方式审查：同一事实尽量一个权威来源；同一语义对象沿调用链保持可追溯名称；错误由真正能处理它的边界负责，其他层只传播既定合同。

## 9. 影响范围审计

修改公共 API、公共常量、配置规则或可观察行为时，搜索全部直接引用，确认生产调用方、测试、样例和文档是否仍符合新合同。不能只修改定义处，也不能留下旧常量或旧假设的引用。

如果外部合同没有变化，只修改私有实现，则只处理真实受影响的直接依赖，不因“同一模块”“同一主题”或顺手清理而扩展范围。

## 10. 审计报告

每个发现至少包含：

- 编号、级别、分类；
- 文件、函数和相关调用路径；
- 当前实现及可观察行为；
- 真实需求或合同依据；
- 技术事实及其来源；
- 复杂度来源：固有约束 / 实现选择 / 历史遗留 / 尚未证实；
- 结论类别：规则/合同违反 / 已证实缺陷 / 最小化或复杂度问题 / 可选建议或范围外观察；
- 具体问题和维护成本；
- 建议处理：保留 / 简化 / 合并 / 删除 / 替换 / 尚未证实；可选建议须与必改项分区；
- 明确的替代实现和受影响文件；并说明修改前后的可观察行为及新增状态、策略或维护成本；
- 测试、文档和调用方如何调整；
- 验收标准。

不要只写“建议优化”“减少封装”“提高可读性”。必须告诉实施者具体怎么改。

## 11. 证据边界与审计权限

审计结论应引用源码位置、生产调用方、合同或测试。若无法确认调用可达性、并发关系或生命周期，标记“尚未证实”，指出需要补充的证据。

用户只要求审计时，输出问题和整改方案，不修改代码。用户要求整改时，才按确认清单实施。
