# 分阶段实施

## 适用范围

已确认方案的多文件修改、模块功能、跨 Service 或跨模块工作。简单局部修改不强制拆阶段。

## 实施步骤

1. 重新读取已确认方案、相关合同和任务直接涉及的规范。
2. 将方案拆成可验证的逻辑阶段，不按文件数量机械拆分。
3. 标明阶段依赖、修改文件、预期行为和验收条件。
4. 按真实依赖顺序实施，优先完成最小闭环。
5. 每个阶段完成后运行与该阶段匹配的检查或测试。
6. 对照确认方案检查是否发生范围扩张。
7. 完成后检查完整调用链、错误路径、状态 owner、资源生命周期和受影响调用方。
8. 汇总实际执行的 build/run/test 与未验证项。

## 实施约束

- 以用户确认的方案为准，不自行增加功能、扩展点、配置、抽象或额外保护机制。
- 不为了拆分任务创建无价值的计划文件、Helper、临时状态或提交。
- 不强制每个阶段提交 Git、创建 Worktree 或启动 Subagent。
- 复用现有结构前先判断它是否确实适合；不能因为“已有”就机械复用。
- 修改前核实可观察合同，修改后逐项对照。
- 不修改第三方源码。
- 与任务无关的清理和重构单独提出，不混入本次实施。
- 测试应验证业务行为和真实边界，不应仅为旧内部结构提供存在理由。

## 中途发现问题

- 发现普通实现错误且不改变合同：按最小方式修复并验证。
- 发现方案遗漏但不改变合同：说明原因，必要时补充最小实施步骤。
- 发现方案与真实源码、第三方 API 或既有合同冲突：暂停冲突部分，提供证据和最小替代建议，等待用户决定。
- 发现必须改变公开合同或用户已确认的设计：暂停相关部分，列明冲突和影响，等待用户决定。
- 发现需要同步的直接调用方、测试或文档：只更新与本次合同变化直接相关的内容，不顺手整理无关文件。
- 发现无法验证的边界：明确标记，不得写成已通过。

## 完成条件

每项实施任务都有明确结果；受影响测试通过；没有未经授权的合同变化；没有顺手扩大范围；报告准确列出验证证据。
