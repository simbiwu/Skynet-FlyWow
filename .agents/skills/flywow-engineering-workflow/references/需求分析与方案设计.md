# 需求分析与方案设计

## 适用范围

新功能、新模块、跨模块修改、公开合同调整和架构讨论。简单且目标明确的局部修改不必走完整流程。

## 1. 从真实问题开始

先明确：

- 用户希望改变什么可观察行为？
- 当前系统实际怎样运行？
- 哪些公开合同和工程约束必须保持？
- 本次明确不做什么？

现有类、Service、Helper、状态和目录只是当前实现，不自动成为新方案的前提。不要先接受现有结构，再围绕它补充层级和保护。

## 2. 核实技术事实和约束来源

凡是会影响方案的技术事实，必须核实到项目实际使用的版本和实现，不得凭名称、印象或通用经验推断。

优先检查：

- 项目实际锁定的第三方版本、分支或 commit；
- 被调用 API 的公开实现、头文件、Lua/C Binding 和参数转换；
- 真实生产调用方、上下游调用链及调用顺序；
- 数据类型、数值范围、单位、时钟语义和溢出行为；
- Service、协程、OS Thread、消息队列、yield 和异步 I/O 的真实执行关系；
- 定时器的注册、重置、取消和回调执行语义；
- 资源 owner、对象生命周期和失败后的真实状态。

明确区分：

- **源码事实**：由当前项目实际使用的源码或公开合同确认；
- **源码推导**：可以从已核实实现推出，但未通过运行验证；
- **测量结果**：由实际 benchmark、profiling 或运行数据得到；
- **假设/待确认**：目前没有足够证据。

假设和待确认事项不得直接变成公共 API、配置上限、业务状态、错误处理或验收合同。缺少证据时，标明未知及其对方案的影响；不要用猜测填空。

尤其不能把第三方库的内部实现细节直接提升为业务规则。例如，内部数据结构使用 32 位字段，不代表对外时钟 API 也是 32 位；必须检查完整的公开返回路径和语言 Binding。

## 3. 独立推导最小方案

先暂时放下当前内部架构，从需求和合同推导能够完整工作的最小实现，再判断如何落到现有工程。

逐项确认：

- 最少需要哪些对象、数据结构和公开 API；
- 每份状态代表什么事实，由谁唯一持有，何时创建、更新和失效；
- 主流程如何从入口走到结果，哪些调用会 yield、I/O 或跨 Service；
- 哪些检查属于真实输入边界，哪些不变量会在后续阶段改变；
- 哪些失败需要由当前模块处理，哪些沿用既有运行时或上层合同；
- 是否存在更直接的现有 API 或数据结构可以完成任务。

新增类、Helper、Manager、Controller、Context、接口、常量、配置、状态、检查、Fallback、重试、恢复和调度器之前，必须说明它解决的当前真实问题、owner、生命周期和真实消费者。没有明确必要性就不加入。

不要为了“通用”“健壮”“商业级”“未来可扩展”预先设计第二种实现、插件点、策略系统或多层抽象。不要为每个函数调用增加重复检查，也不要把一个连续流程机械拆成许多小函数。

选择数据结构时，根据真实操作判断：插入、查询、更新、删除、批量处理、时间精度、取消频率和资源生命周期。不要只因框架已有某种机制，就认定所有业务都应该使用它；也不要只因自定义结构更方便，就重复实现框架已经足够的能力。

## 4. 方案输出要求

默认给出**一个明确推荐方案**，而不是把大量备选方案交给用户选择。只有方案之间在行为、复杂度、性能或合同上存在实质差异时，才比较这些选项，并说明推荐理由。

方案应简洁、具体、可执行，至少说明：

1. 目标与非目标；
2. 现有可观察合同和必须保持的行为；
3. 已核实的关键技术事实及其来源；
4. 推荐的最小设计，包括核心数据、状态 owner 和主要调用流程；
5. 需要修改的文件及其直接影响的调用方；
6. 必要的失败处理和真实边界；
7. 测试、验证方式和验收条件；
8. 明确不引入的抽象、状态、策略或扩展机制。

涉及不熟悉的 Skynet、Lua/C Binding 或 Native API 时，给出少量有上下文的示例代码，说明文件/函数位置、调用者、参数来源和执行结果。不要只贴孤立代码，也不要用大段伪代码替代真实 API 核对。

不要用大量风险清单、架构图或术语堆砌来制造方案完整感。只写会改变设计或验收结论的风险。

## 5. 实施合同

方案一旦由用户确认并授权实施，就是实施合同，不是供 Codex 自由发挥的建议。

合同应明确：

- 允许修改的文件和范围；
- API、参数、返回值、错误语义和外部行为；
- 数据结构、关键状态及其 owner；
- 主要执行顺序和关键生命周期；
- 必须保留的现有能力；
- 测试和验收要求；
- 明确禁止增加的机制。

Codex 不得自行重新设计、扩展合同或补充“认为需要”的功能。若实施中发现方案与源码事实、第三方 API 或现有合同冲突，应停止冲突部分，提供证据和最小替代建议，等待用户决定。

## 6. 影响范围

修改公共 API、公共常量、配置规则、返回合同或其他可观察行为时，搜索所有直接引用，处理必要的生产调用方、测试、样例和文档，避免留下旧合同依赖。

如果只修改私有实现且外部合同不变，不需要为了“保持一致”修改所有同领域文件。影响范围由实际依赖和合同变化决定：既不能只改定义处，也不能借机全仓重构。

## 7. 输出边界

用户要求讨论或方案时，只提交方案，不修改文件。用户已经确认方案并授权实施时，直接进入实施，不重复确认。只询问会实质改变合同或推荐方案的关键问题；已经能从源码或工程文档确定的信息，不要求用户重复提供。
