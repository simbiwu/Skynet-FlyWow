# 反模式与架构重置

## 目标

本文件用于解决一种常见审计失效：审计者先接受当前架构，再用调用者、测试、文档、保护逻辑和历史选择解释每个组件为什么不能删除。

架构重置不是默认重写模块，而是在审计阶段暂时不受现有内部结构约束，独立推导一个更简单的完整实现，再做证据化比较。

## 架构重置步骤

### 1. 抽离真实需求

先记录外部可观察行为、公开合同、真实业务约束和不可改变的技术边界。暂时不把现有类、接口、状态、目录、Helper 和测试结构视为需求。

### 2. 独立推导最小实现

假设当前内部实现不存在，从入口到结果重新设计最直接的流程。明确需要哪些对象、状态、调用、验证、资源和失败处理。不得为了代码短而忽略真实并发、隔离、授权、生命周期或公开合同。

### 3. 核验关键技术事实

涉及第三方库、运行时、语言 Binding、线程、协程、时钟、定时器或数据类型时，先确认项目实际使用的版本和公开行为。不能把内部字段、旧注释、测试假设或 API 名称当作技术合同。

### 4. 还原旧设计

追踪当前生产调用链、数据流、状态写入/读取、错误传播、yield/RPC、资源创建/释放和测试覆盖。标出每个中间层的输入、输出和实际决策。

### 5. 追溯复杂度来源

对每个可疑结构问：

- 它解决哪个当前真实问题？
- 问题来自业务/运行时约束，还是由前一个内部结构引入？
- 若删除其上游对象，这个结构及其保护机制是否仍然需要？
- 现有生产路径能否触发它要防御的事件？
- 是否有更直接的实现保持相同外部行为？
- 相关限制、常量和状态来自真实需求，还是未经验证的实现假设？

### 6. 重新评估保护机制

保护机制不能脱离保护对象单独判断。某个 Context 的生命周期管理可能正确，但若 Context 本身没有必要，其生命周期机制也可能随之消失。反之，简化后仍然存在的资源、信任边界、并发和失败风险必须在新设计中得到明确处理。

### 7. 比较新旧完整设计

至少比较：

- 外部行为和公开合同；
- 调用层级和跨模块跳转；
- 类、函数、record 和状态数量；
- 重复验证、数据复制和错误转换；
- 生命周期和资源 owner；
- 必要的隔离、并发与安全保证；
- 测试需要验证的行为；
- 维护者理解主流程所需掌握的概念。

不使用代码行数、类数量或抽象层数的简单加总替代判断。重点是维护成本和理解成本。

### 8. 形成可执行整改

逐项标明保留、简化、合并、删除、替换或尚未证实。对删除和替换项说明生产调用方如何迁移、测试如何改为验证行为、内部文档如何同步、公开合同是否变化。

## 常见反模式

### 无价值中间层

Manager、Controller、Wrapper、Helper 只转发参数或改名，没有独立策略、状态 owner 或生命周期价值。优先评估直接调用。

### 投机性通用设计

为未来可能出现的第二种实现、策略或消费者提前增加接口、Factory、Provider、插件点和配置。没有真实需求时不进入实现。

### 状态冗余

同一事实由多个变量、record 或模块分别保存，靠同步维持一致。优先保留唯一权威状态，其余在使用处派生。

### 数据包装和换名

同一语义对象沿调用链不断复制、包装或改成泛名。若语义没有变化，优先直接传递并保持名称一致；语义变化时才创建新对象。

### 重复防御

相同条件在多个内部函数反复检查。验证应对应真实不可信边界、数据变化点或状态有效性变化点，不对应函数调用次数。

### 防御性状态和理论路径

为当前生产合同下不可达的重复调用、重放或乱序事件增加状态和门禁。必须从生产入口证明可达性，不能仅用测试构造输入证明它必要。

### 保护机制自我证明

一个内部对象引入了复杂生命周期、清理、同步和恢复机制，随后又以这些机制完善为理由保留对象。必须回到对象的真实职责和需求重新判断。

### 测试和文档绑定内部实现

测试若只验证内部类、Helper 或旧调用顺序，应评估是否改为验证外部行为和必要边界。公开合同测试必须保留；内部实现文档可随设计更新。不能因测试或文档引用而固化历史结构。

## 不得误删的复杂度

以下内容必须根据真实工程证据保留或重新实现：

- 外部不可信输入的必要验证；
- 真实的授权和身份校验；
- 跨 yield/RPC 后可能失效的连接身份或资源有效性检查；
- 多线程共享可变状态所需的同步；
- 明确的资源所有权、释放和关闭顺序；
- 对外公开 API、协议、错误语义和兼容合同；
- 真实需要的模块隔离和故障边界；
- 真实失败路径和必要恢复行为。

这些项目也不能自动免于审计：必须确认保护对象、边界和风险真实存在，而不是由多余设计制造。

## 验收标准

一次架构重置审计合格，至少要能：

1. 独立写出不依赖现有内部结构的最小流程；
2. 识别有调用者但可被更直接调用替代的中间层；
3. 区分业务行为测试与内部实现绑定测试；
4. 区分公开合同与内部文档；
5. 找出同一状态/数据沿调用链重复传递、检查或转换；
6. 追溯保护机制是否只服务于多余的内部对象；
7. 提出完整替代设计，并明确新设计仍需保留的保护；
8. 对合同变化、证据不足和未验证边界如实标记。
